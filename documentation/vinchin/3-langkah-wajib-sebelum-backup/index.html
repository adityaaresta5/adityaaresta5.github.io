Model mental

Vinchin adalah “mesin” di tengah tiga koneksi

Semua modul Vinchin—VM Backup, Restore, Backup Copy, DR—berjalan di atas satu mesin pusat. Mesin ini hanya bisa bekerja jika tiga koneksi berikut tersedia:

  • 1Izin (license): tanpa lisensi valid, job backup dan restore ditolak sistem.
  • 2Sumber data (hypervisor): host harus terhubung dan diotorisasi agar VM bisa dibaca.
  • 3Tujuan data (storage): harus ada repository dengan kapasitas dan status yang sehat.

Jika satu koneksi putus, rantai backup gagal—sering kali bukan karena mesin backup-nya bermasalah.

Masuk ke Web Console Vinchin

Semua konfigurasi Vinchin dilakukan dari browser. Sebelum menyentuh lisensi atau storage, pastikan kamu bisa membuka dashboard dan login dengan benar.

Apa yang kamu lakukan

  1. Pastikan server Vinchin menyala dan berada di jaringan yang sama dengan komputermu (atau bisa dijangkau lewat VPN).
  2. Buka browser modern, lalu akses https://<IP-Server-Vinchin>. Gunakan https, bukan http.
  3. Jika muncul peringatan sertifikat “Not secure / self-signed”, pilih Advanced → Proceed. Ini normal pada instalasi baru karena sertifikat bawaan belum diganti.
  4. Masukkan kredensial awal: username admin dan password 123456, lalu klik Login.
  5. Setelah dashboard terbuka, segera ganti password default lewat System › User Management agar tidak menjadi celah keamanan.
Server menyala IP server diketahui Port 443 terbuka Browser modern

Kenapa langkah ini penting

Web Console adalah satu-satunya pintu konfigurasi yang nyaman. Hampir semua pekerjaan—lisensi, inventaris, storage, jadwal backup, restore—dilakukan dari sini. Kalau login saja tidak berhasil, langkah berikutnya tidak mungkin dikerjakan.

Mengganti password default sejak awal juga mencegah orang lain masuk dan mengubah konfigurasi backup.

Analogi sederhana

Anggap Web Console sebagai ruang kontrol gedung. Kamu tidak perlu turun ke ruang mesin (CLI Linux), cukup masuk lewat pintu utama dengan kartu akses (username & password), lalu semua tombol penting ada di depan mata.

Tips keamanan & jebakan umum

  • Jangan buka port 443 langsung ke internet. Tempatkan di jaringan manajemen atau akses lewat VPN.
  • Catat IP dan kredensial baru di password manager. Vinchin tidak bisa “reset” dari halaman login.
  • Jika halaman tidak terbuka: cek alamat IP, kabel/jaringan, firewall, dan pastikan service web Vinchin berjalan.
  • Peringatan sertifikat akan hilang setelah kamu memasang sertifikat resmi (opsional untuk lab).
Cek pemahaman: kenapa harus https, bukan http?
Karena halaman login mengirim username dan password. Dengan HTTPS, lalu lintas terenkripsi sehingga kredensial tidak mudah disadap di jaringan. Vinchin memang berjalan di port web aman (443).
Cek pemahaman: apakah wajib mengganti password sebelum backup?
Tidak wajib secara teknis, tetapi sangat disarankan. Password default 123456 diketahui publik. Ganti sebelum server dipakai di lingkungan nyata, bukan setelah konfigurasi selesai.

Registrasi Lisensi: Thumbprint & Upload License

Lisensi bukan sekadar formalitas. Di Vinchin, lisensi menentukan fitur yang terbuka, kuota CPU socket/VM yang boleh diproteksi, dan masa berlaku. Tanpa lisensi, job backup/restore akan ditolak.

Apa yang kamu lakukan

  1. Buka System › System License. Periksa panel License Info: edisi, tipe lisensi, kuota VM/File Backup, dan tanggal kedaluwarsa.
  2. Klik Download Thumbprint. Simpan file identitas server tersebut di komputermu.
  3. Kirim file thumbprint ke support@vinchin.com (atau partner resmi tempat kamu membeli) bersama informasi pembelian dan hostname server.
  4. Vendor akan mengirim balik file lisensi ber-ekstensi .lic yang terikat pada thumbprint servermu.
  5. Kembali ke halaman yang sama, klik Upload License, pilih file .lic, lalu konfirmasi.
  6. Pastikan status berubah dari Trial/unlicensed menjadi lisensi aktif, dan kuota sesuai pembelian. Baru lanjut ke Fondasi 2.
Download ThumbprintAmbil identitas unik server dari menu System License.
Kirim ke vendorSertakan bukti pembelian & hostname lewat email/partner.
Terima file .licLisensi dibuat khusus untuk thumbprint servermu.

Fungsi lisensi

Membuka fitur backup/restore dan menetapkan kuota proteksi—misalnya jumlah CPU socket host atau jumlah VM yang boleh diproteksi.

Analogi

Thumbprint seperti nomor rangka kendaraan, sedangkan file lisensi seperti STNK. STNK hanya berlaku untuk kendaraan dengan nomor rangka tersebut.

Jika belum berlisensi

Sistem menampilkan status Unlicensed dan menolak semua job backup/restore. Jangan buang waktu membuat jadwal backup sebelum lisensi aktif.

Detail yang sering terlewat

  • Thumbprint ≠ file lisensi. Thumbprint adalah “sidik jari” server; file .lic adalah izin yang diterbitkan vendor berdasarkan sidik jari itu.
  • Jangan mengganti komponen utama atau reinstall server sebelum lisensi selesai diproses. Thumbprint bisa berubah dan lisensi tidak lagi cocok.
  • Di screenshot, License Type = CPU Socket(s) dengan kuota VM Backup CPU Socket(s) 1/50 dan File Backup Hosts 1/30. Angka aktual mengikuti edisi yang dibeli.
  • Simpan file .lic dan thumbprint di tempat aman—berguna saat audit atau pemulihan server.
  • Jika upload gagal, cek ekstensi file, apakah lisensi dibuat untuk server yang benar, dan jam sistem server.
Cek pemahaman: kenapa lisensi tidak bisa dipakai di server lain?
Karena lisensi diikat ke thumbprint—identitas hardware unik server (antara lain kombinasi informasi hardware/CPU/MAC). Di server lain, thumbprint berbeda, sehingga lisensi dianggap tidak cocok. Ini mencegah satu lisensi dipakai berulang tanpa izin.
Cek pemahaman: apa yang terjadi kalau kuota CPU socket habis?
Host berikutnya tidak bisa diotorisasi pada langkah 2.2. Kamu perlu menambah kuota lisensi, atau menganalisis apakah ada host yang sudah tidak dipakai dan bisa dilepas otorisasinya.

Menambahkan Virtual Infrastructure

Vinchin harus “mengenal” hypervisor-mu sebelum bisa melihat VM. Di langkah ini kamu menghubungkan server backup ke vCenter/ESXi (atau platform lain) menggunakan kredensial API.

Apa yang kamu lakukan

  1. Buka Resources › Virtual Infrastructure, lalu klik Add.
  2. Pilih Platform yang sesuai—contoh di modul ini VMware vSphere.
  3. Isi IP/Domain pengelola hypervisor. Untuk cluster VMware, gunakan alamat vCenter; untuk host tunggal, gunakan alamat ESXi.
  4. Masukkan Username dan Password akun yang punya hak membaca inventaris, membuat snapshot, dan mengakses disk VM.
  5. Beri Name yang mudah dikenali (misalnya VMware-Prod), lalu klik OK.
  6. Tunggu proses verifikasi. Jika kredensial benar, platform akan muncul di daftar dan Vinchin mulai membaca inventaris VM.

Kenapa langkah ini penting

Tanpa koneksi ke hypervisor, Vinchin tidak punya daftar VM, datastore, atau network. Koneksi inilah yang memungkinkan Vinchin membaca inventaris, membuat snapshot, lalu mengalirkan data disk ke storage backup.

Analogi sederhana

Ini seperti menambahkan kontak penting ke ponsel: kamu memasukkan alamat (IP), identitas (username), dan kunci akses (password). Setelah terhubung, barulah kamu bisa menelepon—atau dalam konteks ini, membaca data VM.

Jebakan umum saat menambahkan infrastruktur

  • Akun read-only. Vinchin butuh hak untuk snapshot dan membaca virtual disk. Gunakan akun integrasi dengan hak yang sesuai.
  • Memakai ESXi padahal ada cluster. Jika VM bisa berpindah host (DRS), hubungkan ke vCenter dan otorisasi semua host di cluster.
  • 2FA / lockout. Akun API sebaiknya tidak memakai autentikasi dua faktor yang memblokir sesi otomatis.
  • Port/jaringan. Pastikan server Vinchin bisa mencapai vCenter/ESXi di port yang dibutuhkan dan DNS-nya benar.
  • Password berubah. Jika password akun diganti, edit platform di Vinchin dan perbarui kredensialnya.
Cek pemahaman: kapan memakai vCenter dan kapan memakai ESXi?
Gunakan vCenter jika kamu mengelola beberapa host dalam cluster, karena Vinchin bisa melihat seluruh cluster dan VM yang berpindah host. Gunakan ESXi hanya jika host berdiri sendiri (standalone) dan tidak dikelola vCenter.
Cek pemahaman: apakah menambah infrastruktur otomatis mengizinkan backup?
Belum. Menambahkan platform hanya membangun koneksi dan membaca inventaris. Host masih berstatus Unauthorized sampai kamu melakukan otorisasi di langkah 2.2.

Otorisasi Host: jangan lewatkan langkah ini

Host yang sudah terhubung belum tentu boleh diproteksi. Otorisasi adalah momen Vinchin mengalokasikan kuota lisensi ke host tersebut dan memberi izin teknis untuk snapshot serta membaca disk VM.

Apa yang kamu lakukan

  1. Di daftar Virtual Infrastructure, perhatikan kolom Status. Host baru biasanya berstatus Unauthorized (kuning/merah).
  2. Klik tombol Auth pada baris platform yang ingin diotorisasi.
  3. Di jendela Host Authorization, centang host target. Untuk cluster, centang semua host agar VM yang berpindah host tetap bisa dibackup.
  4. Klik Authorize. Status host berubah menjadi Authorized / All Authorized, dan kuota lisensi berkurang sesuai jumlah CPU socket host.
  5. Ulangi untuk platform lain jika ada. Pastikan total kuota tidak terlampaui.

Kenapa otorisasi wajib?

Otorisasi punya dua fungsi sekaligus: legal (mengalokasikan kuota lisensi) dan teknis (memberi izin engine backup memanggil snapshot serta membaca stream disk host). Tanpa itu, job backup gagal di langkah pertama dengan pesan VM berstatus unauthorized.

Analogi sederhana

Host yang terhubung seperti tamu yang sudah sampai di lobi. Otorisasi adalah memberi gelang akses: baru setelah itu ia boleh masuk ke area backup. Gelangnya terbatas, jadi kuota harus dijaga.

Peringatan dari layar Vinchin

Jika beberapa host dikelola oleh VM Manager yang sama (cluster), lakukan full authorization. Bila VM berpindah ke host yang belum diotorisasi—misalnya karena DRS/vMotion—maka VM backup job akan gagal.

Tips operasional

  • Authorize seluruh host dalam cluster, bukan hanya host tempat VM berada hari ini.
  • Tambahkan host baru ke perencanaan kuota sebelum scale-out. Host tanpa kuota tidak bisa diotorisasi.
  • Jika host dihapus/diganti, lepaskan otorisasinya agar kuota kembali tersedia.
  • Status All Authorized di daftar platform berarti seluruh host di bawah platform itu sudah diotorisasi.
Cek pemahaman: apa bedanya “terhubung” dan “terotorisasi”?
Terhubung berarti Vinchin bisa berkomunikasi dengan hypervisor dan membaca inventaris. Terotorisasi berarti host tersebut sudah dialokasikan kuota lisensi dan diizinkan untuk menjalankan backup/restore. Host bisa terhubung tetapi masih Unauthorized.

Sinkronisasi Inventaris VM: auto-refresh vs manual sync

Setelah host terhubung, daftar VM di Vinchin bisa tertinggal dari kondisi hypervisor. Di sinilah auto-refresh dan tombol Sync berperan: memastikan VM baru, VM yang dipindah, atau VM yang dihapus ikut terbarui.

Apa yang kamu lakukan

  1. Atur Auto-refresh in every [ X ] minute(s) di kanan atas. Nilai 5 menit adalah awal yang wajar, lalu klik Save.
  2. Untuk pembaruan seketika, klik tombol Sync pada baris platform.
  3. Buka detail platform (klik IP/namanya) untuk memastikan VM yang kamu harapkan sudah muncul.
  4. Jika VM baru tetap tidak muncul, cek kembali koneksi/kredensial dan apakah VM berada di host yang sudah diotorisasi.

Kenapa perlu disinkronkan?

Vinchin menyimpan salinan inventaris agar daftar VM cepat dibuka. Salinan ini harus diperbarui ketika ada VM baru, VM dipindah, di-rename, atau dihapus. Kalau tidak, kamu bisa memilih VM yang sudah tidak ada— atau tidak menemukan VM yang seharusnya dibackup.

Analogi sederhana

Auto-refresh seperti resepsionis yang memperbarui daftar tamu setiap 5 menit. Sync seperti menelepon resepsionis sekarang juga karena kamu baru menambah satu tamu.

Auto-refresh

Pembaruan berkala sesuai interval. Cocok untuk operasi normal. Interval terlalu kecil bisa membebani API hypervisor.

Manual Sync

Memaksa pembacaan inventaris saat itu juga. Berguna setelah membuat VM atau sebelum menyusun jadwal backup.

Sync ≠ Backup

Sync hanya memperbarui daftar. Ia tidak membuat restore point dan tidak menggantikan backup job.

Jebakan & tips

  • VM baru “tidak ada” di Vinchin sering kali hanya masalah inventaris belum disinkronkan—bukan backup rusak.
  • Setelah migrasi VM antar-host, lakukan Sync dan pastikan host tujuan sudah diotorisasi.
  • Jangan mengatur auto-refresh terlalu agresif (misalnya tiap menit) untuk lingkungan besar; pilih interval yang seimbang.
  • Jika Sync terus gagal, periksa koneksi, kredensial, dan status host—bukan hanya menekan tombol berulang kali.
Cek pemahaman: VM baru dibuat, tapi tidak muncul. Apa langkah paling cepat?
Klik Sync pada platform terkait. Jika tetap tidak muncul, periksa koneksi/kredensial dan pastikan VM berada di host/cluster yang sudah diotorisasi. Auto-refresh juga akan memperbarui daftar, tetapi mungkin baru pada interval berikutnya.

Menambahkan Backup Storage (Repository)

Sumber sudah terhubung, izin sudah ada. Sekarang Vinchin butuh tempat untuk menulis data. Di sinilah kamu menentukan jenis storage, partisi/disk yang dipakai, nama repository, dan tujuannya.

Apa yang kamu lakukan

  1. Buka Resources › Storage, klik Add.
  2. Pilih Storage Type sesuai media yang tersedia: Partition/Local Disk, NFS, CIFS, iSCSI, Fibre Channel, atau Cloud.
  3. Pilih Node IP/Domain—backup node yang memiliki akses langsung ke storage tersebut.
  4. Centang Storage Resource (partisi/disk target). Pastikan kapasitas dan nama device sudah benar.
  5. Beri Name yang deskriptif, misalnya PartitionBackup, lalu tentukan Storage Objective.
  6. Aktifkan Storage Alert dan atur threshold (lihat langkah 3.2), lalu klik OK.
  7. Konfirmasi pilihan Format atau Import (lihat langkah 3.3), lalu verifikasi repository muncul di daftar dengan kapasitas terbaca.

Klik salah satu tipe untuk melihat kapan sebaiknya dipakai, kelebihannya, dan hal yang perlu diwaspadai.

Partition / Local Disk

Disk atau partisi yang terpasang langsung di server backup. Paling sederhana dan cepat, cocok untuk lab atau kebutuhan restore cepat.

Perhatian: kapasitas terbatas pada server itu; tidak melindungi dari kegagalan server. Gunakan bersama Backup Copy/Archive untuk aturan 3-2-1.

Cocok: lab, backup primerKecepatan: tinggi

Kenapa langkah ini penting

Backup tanpa tujuan ibarat menyalin file tanpa hard disk. Repository adalah tempat semua restore point disimpan. Salah memilih partisi atau objective bisa membuat data tertaruh di media yang salah—atau kapasitas cepat habis.

Analogi sederhana

Ini seperti memilih gudang arsip: kamu menentukan lokasi gudang (storage type), rak yang dipakai (resource), label gudang (name), dan apakah gudang itu untuk arsip aktif atau arsip cadangan (objective).

Backup

Repository primer untuk restore cepat. Job backup menulis restore point ke sini.

Backup Copy

Salinan tambahan dari backup primer, biasanya ke lokasi/media berbeda untuk redundansi.

Archive

Penyimpanan jangka panjang untuk retensi lama, sering kali ke media/offsite yang lebih murah.

Perkiraan kapasitas (kasar)

Kebutuhan ≈ data terpakai × jumlah restore point × faktor perubahan

Faktor perubahan berkisar sekitar 0,3–1 tergantung pola perubahan data, jenis backup (full/incremental), serta kompresi/deduplikasi. Angka ini hanya perkiraan awal; pantau pemakaian nyata setelah beberapa siklus backup dan sisakan ruang untuk pertumbuhan.

Jebakan yang harus dihindari

  • Memilih partisi sistem operasi Vinchin—bisa merusak sistem dan datanya.
  • Mencampur objective tanpa strategi; backup primer yang penuh tidak otomatis menjadi arsip.
  • Mengabaikan performa storage jaringan. NFS/CIFS/iSCSI yang lambat memperpanjang jendela backup.
  • Menganggap storage lokal sudah cukup. Jika server rusak, backup di disk yang sama bisa ikut hilang.
  • Tidak menyisakan ruang kosong. Repository yang terlalu penuh membuat job gagal di tengah jalan.
Cek pemahaman: apa bedanya “Backup” dan “Backup Copy”?
Backup adalah repository tujuan job backup utama—tempat restore point pertama dibuat. Backup Copy adalah salinan tambahan dari backup tersebut, biasanya ke storage/lokasi lain, untuk meningkatkan redundansi dan mendukung strategi 3-2-1.

Storage Alert: peringatan sebelum gudang penuh

Repository yang penuh di tengah proses backup bukan hanya membuat job gagal. Snapshot di hypervisor bisa tertinggal dan memperlambat VM produksi. Storage Alert memberi kamu waktu untuk bertindak sebelum itu terjadi.

Apa yang kamu lakukan

  1. Pada form storage, set Storage Alert ke On.
  2. Pilih Threshold by: Percentage (misalnya 20%) atau Size (misalnya 10 GB tersisa).
  3. Isi nilai threshold sesuai kapasitas repository dan ukuran backup terbesar.
  4. Simpan storage, lalu pastikan notifikasi email sudah dikonfigurasi di System Settings agar peringatan benar-benar terkirim.

Kenapa alert itu penting

Jika storage habis (0 bytes free) saat backup berjalan, job akan gagal. Lebih buruk lagi, snapshot bisa tertinggal di hypervisor (stale snapshot) sehingga ruang datastore produksi ikut membengkak dan performa VM menurun.

Dengan peringatan dini, kamu punya waktu untuk menambah kapasitas, menghapus restore point lama, atau memindahkan backup sebelum masalah terjadi.

Analogi sederhana

Storage Alert seperti lampu indikator bensin. Mobil masih bisa jalan, tetapi kamu diberi peringatan sebelum benar-benar kehabisan bahan bakar di tengah perjalanan.

Cara memilih threshold

  • Percentage cocok jika ukuran repository bervariasi; 15–20% adalah titik awal yang umum.
  • Size cocok jika kamu ingin ambang yang pasti—misalnya sisa 10 GB, cukup untuk satu backup terbesar.
  • Pastikan ruang yang tersisa saat alert masih cukup untuk menyelesaikan setidaknya satu backup penuh.
  • Alert hanya berguna jika email/SMTP sudah dikonfigurasi dan diuji. Tanpa itu, peringatan tidak sampai ke admin.
  • Jangan menunggu 95% terpakai; pada titik itu waktu untuk bertindak sudah terlalu sempit.
Cek pemahaman: alert 20% berarti apa?
Sistem memberi peringatan ketika ruang kosong tersisa kurang dari 20% dari kapasitas repository—bukan ketika pemakaian mencapai 20%. Pada kapasitas 1 TB, alert muncul saat sisa ruang di bawah sekitar 200 GB.

Format vs Import: pilihan yang tidak bisa dibatalkan

Setelah menekan OK pada Storage Settings, Vinchin menanyakan satu hal penting: apakah disk ini kosong dan boleh diformat, atau sudah berisi backup Vinchin yang ingin diimpor? Salah pilih bisa menghapus data secara permanen.

Import Backups pertahankan

Gunakan jika disk/partisi sudah berisi repository Vinchin dari server lain atau server lama.

  • Riwayat restore point dan katalog VM ikut terbaca.
  • Kunci skenario disaster recovery setelah server rusak.
  • Tidak menghapus data yang sudah ada.
  • Pastikan disk berasal dari versi Vinchin yang kompatibel.

Format hapus total

Gunakan hanya untuk disk/partisi baru atau kosong yang memang boleh dikosongkan.

  • Menyiapkan struktur file optimal untuk Vinchin.
  • Seluruh data pada disk akan hilang permanen.
  • Tidak ada undo atau recycle bin.
  • Periksa dua kali nama device sebelum konfirmasi.
Latihan keputusan · disk ini harus diapakan? interaktif

Pilih kondisi disk, lalu lihat tindakan yang tepat beserta alasannya.

Peringatan risiko data

Format menghapus total seluruh data pada partisi/disk tersebut. Tidak ada tombol undo. Sebelum mengonfirmasi, cocokkan nama device (misalnya /dev/sdb1) dengan daftar disk di sistem, dan pastikan kamu tidak sedang menunjuk disk sistem operasi atau disk berisi data produksi.

Kenapa fitur Import ada?

Import adalah jalur penyelamat saat server Vinchin rusak total tetapi disk repository masih sehat. Kamu bisa memasang server Vinchin baru, menghubungkan kembali disk lama, memilih Import Backups, lalu seluruh katalog dan restore point lama terbaca tanpa harus menyalin ulang data dari awal.

Checklist setelah storage berhasil ditambahkan

  • Repository muncul di Storage List dengan status sehat dan kapasitas terbaca.
  • Objective sesuai rencana (Backup / Backup Copy / Archive).
  • Storage Alert aktif dan email notifikasi sudah diuji.
  • Kapasitas tersisa cukup untuk setidaknya satu siklus backup penuh.
  • Baru setelah ini kamu siap membuat Backup Job pertama.
Cek pemahaman: kapan memilih Import, bukan Format?
Pilih Import Backups hanya jika disk tersebut sudah berisi repository Vinchin yang ingin dipertahankan—misalnya setelah server lama rusak atau saat migrasi. Jika disk baru/kosong, pilih Format. Jika berisi data lain yang bukan repository Vinchin, jangan format; pindahkan datanya terlebih dahulu.

Kamus istilah

Istilah yang muncul di modul ini

Bacaan singkat agar istilah teknis tidak menghambat pemahaman saat mengikuti langkah-langkah di atas.

Hypervisor

Perangkat lunak yang menjalankan dan mengelola virtual machine, misalnya VMware ESXi, vCenter, atau OLVM.

VM (Virtual Machine)

Komputer virtual berisi sistem operasi dan aplikasi yang berjalan di atas hypervisor.

Snapshot

Penanda kondisi disk VM pada titik waktu tertentu. Vinchin memanfaatkannya untuk mengambil data secara konsisten.

Thumbprint

Identitas unik server Vinchin, dipakai vendor untuk menerbitkan lisensi yang hanya cocok di server tersebut.

Agentless

Metode backup tanpa memasang agent di dalam VM. Vinchin berkomunikasi langsung lewat API hypervisor.

Repository

Tempat penyimpanan hasil backup—bisa berupa partisi lokal, NFS/CIFS, SAN, atau cloud.

Restore point

Satu salinan data pada waktu tertentu yang bisa dipulihkan kembali ke VM atau lokasi lain.

vMotion / DRS

Fitur VMware untuk memindahkan VM antar-host secara otomatis. Karena itu semua host cluster perlu diotorisasi.

3-2-1 Rule

Prinsip backup: 3 salinan data, di 2 media/teknologi berbeda, dengan 1 salinan di lokasi terpisah.

FAQ

Pertanyaan yang sering muncul

Beberapa kebingungan umum saat pertama kali menyiapkan Vinchin Backup & Recovery.

Apakah lisensi harus aktif sebelum menambah infrastruktur?
Secara teknis kamu bisa menambahkan platform lebih dulu, tetapi host tidak akan bisa menjalankan backup sebelum lisensi aktif. Urutan yang disarankan tetap: lisensi → infrastruktur → otorisasi → storage, agar tidak ada pekerjaan yang terbuang.
Apakah setelah storage ditambahkan bisa langsung backup?
Belum. Storage hanyalah fondasi ketiga. Kamu masih perlu membuat Backup Job di menu VM Backup › Backup—memilih VM, jadwal, retensi, dan repository tujuan—lalu menjalankannya.
Apa bedanya Backup, Backup Copy, dan Archive?
Backup adalah repository primer tempat job backup menulis. Backup Copy membuat salinan tambahan ke lokasi/media lain. Archive menyimpan data jangka panjang untuk retensi lama. Ketiganya bisa dipadukan untuk strategi 3-2-1.
Apakah semua platform bisa agentless?
Tidak. VMware vSphere dan Huawei FusionCompute umumnya agentless (tanpa plugin). Platform seperti Citrix XenServer/XCP-ng, oVirt/RHV/OLVM, OpenStack, dan Sangfor HCI membutuhkan Vinchin Backup Plugin pada host fisik.
Kalau server Vinchin rusak, apakah backup hilang?
Tidak, selama disk repository masih utuh. Pasang server Vinchin baru, hubungkan kembali disk tersebut, lalu pilih Import Backups saat menambahkan storage. Katalog dan restore point lama akan terbaca kembali.
Apakah mengubah IP server memengaruhi lisensi?
Lisensi Vinchin terikat pada thumbprint (identitas hardware), bukan sekadar alamat IP. Namun perubahan besar pada server—reinstall, penggantian komponen utama—bisa mengubah thumbprint. Jika ragu, konfirmasikan ke vendor sebelum melakukan perubahan besar.
Berapa kapasitas storage yang ideal?
Tidak ada angka tunggal. Perhitungkan jumlah data yang diproteksi, jumlah restore point yang ingin disimpan, pola perubahan data, serta pertumbuhan. Sisakan ruang kosong yang cukup untuk setidaknya satu backup penuh agar job tidak gagal saat storage mendekati penuh.
