Apa yang dilakukan

  1. Login ke konsol Vinchin sebagai admin (rekaman memakai https://172.18.14.12).
  2. Di sidebar, buka S3 Backup > Backup.
  3. Pilih job Object Storage Backup Job1 di panel kiri.
  4. Baca panel Restore Point List: timestamp, tipe, ukuran, dan storage.
  5. Catat timestamp-nya di tiket sebelum lanjut.

Mengapa penting

Restore point adalah sumber kebenaran job restore. Salah memilih titik berarti memulihkan data dari waktu yang salah—walau semua langkah berikutnya benar. Tipe Full Backup juga menjelaskan mengapa objek bisa dipulihkan tanpa mencari rantai incremental.

Analogi praktis

Restore point seperti halaman buku harian. Kamu memilih halaman yang ingin dibaca ulang, bukan menulis halaman baru. Tanggal dan jam di halaman itu harus cocok dengan kejadian yang ingin dipulihkan.

Jebakan umum

  • Membuka VM Backup atau NAS Backup, bukan S3 Backup.
  • Menganggap restore point terbaru selalu paling sehat; bisa saja snapshot terbaru memuat data yang sudah rusak.
  • Menghapus backup lama sebelum restore selesai—rantai restore point bisa ikut rusak.

Pro-tip

Tulis trio ini di tiket: nama job + timestamp + ukuran. Saat ada dua job dengan nama mirip, trio ini menyelamatkanmu dari restore ke titik yang salah.

  • Access key masih valid untuk baca, tetapi tidak punya izin PutObject.
  • Memilih Object Storage untuk data yang sebenarnya harus mendarat di share NFS/SMB.

Pro-tip

Gunakan bucket/tenant khusus restore dan kredensial terpisah dari produksi. Jika job salah arah, dampaknya terkurung di ruang yang bisa dibuang.

Step 3 punya tiga tab: General, Transmission, dan Advanced. Rekaman memakai 3 transfer threads, retry 60× dengan interval 30 detik, serta kebijakan Overwrite untuk objek bernama sama.

Apa yang dilakukan

  1. Buka tab General Strategy > Advanced; pastikan Transfer Threads = 3.
  2. Buka Transmission Strategy; isi Retry Attempts 60, Retry Interval 30.
  3. Biarkan Backup Proxy dan Encrypted Transfer off sesuai lab.
  4. Buka Advanced Strategy; biarkan Remove Prefix off.
  5. Set Handle Same-name Objects = Overwrite, lalu Next.

Mengapa penting

Threads mengatur paralelisme; retry meredam gangguan sementara S3 (timeout/5xx). Kebijakan nama menentukan apakah objek lama ditimpa, dilewati, atau diganti nama—inilah titik di mana restore bisa mengubah data produksi secara permanen.

Analogi praktis

Threads = jumlah kurir. Retry = berapa kali kurir kembali ke alamat yang gagal. Same-name policy = apa yang dilakukan jika kotak tujuan sudah berisi paket dengan label yang sama.

Jebakan umum

  • Overwrite ke prefix produksi menghapus objek bernama sama tanpa dialog tambahan.
  • Threads terlalu tinggi membanjiri bandwidth dan membuat job lain timeout.
  • Encrypted Transfer OFF di jaringan publik membuka payload untuk disadap.
  • Retry 60 × 30 detik membuat kegagalan permanen baru terlihat setelah ±30 menit.

Pro-tip

Mulai dari 3 thread, pantau grafik job, lalu naikkan bila target tidak jenuh. Untuk restore ke prefix baru, Skip lebih aman saat pengujian; ubah ke Overwrite hanya setelah disetujui.

  • Me-refresh halaman saat job berjalan dan kehilangan konteks log.
  • Mengabaikan progress yang macet lama—padahal target sedang menolak objek.
  • Tidak mencatat durasi; baseline ini berguna untuk restore berikutnya.

Pro-tip

Buka Run Log di tab terpisah dan catat waktu mulai/selesai. Untuk dataset 1.42 GB, rekaman selesai sekitar 59 detik; angka ini jadi pembanding saat kecepatan turun drastis.

  • Lifecycle rule menghapus hasil restore sebelum sempat diverifikasi.

FAQ

Pertanyaan yang paling sering muncul

Jawaban singkat berbasis alur di rekaman dan praktik restore object storage pada umumnya.

Apakah restore S3 bisa diarahkan ke file server atau NAS?

Bisa. Dropdown Restore to menyediakan Object Storage, File Server, dan NAS Share. Namun path dan kredensialnya berbeda: object storage memakai bucket + prefix, sedangkan file server/NAS memakai share + folder. Pilih sesuai tujuan akhir, bukan sekadar yang sudah terisi.

Apakah “Recover to original path” aman?

Aman hanya jika niatmu memang menimpa objek di path asal. Untuk insiden produksi, pilih Manual select path dan folder baru. Dengan begitu kamu bisa membandingkan hasil restore sebelum mempromosikannya.

Berapa lama job restore berjalan?

Rekaman menyelesaikan 1.42 GB dalam ±59 detik dengan 3 thread. Durasi nyata dipengaruhi ukuran objek, latensi endpoint, bandwidth, jumlah thread, dan antrean job. Gunakan angka ini sebagai baseline, bukan SLA.

Apa efek “Handle Same-name Objects: Overwrite”?

Jika key objek sudah ada di tujuan, Vinchin akan menimpa objek lama dengan versi dari restore point. Di bucket dengan versioning, versi lama bisa tetap tersimpan sebagai noncurrent version—tetapi jangan mengandalkannya sebagai backup.

Kenapa job berhenti di Pending?

Job baru masuk antrean. Penyebab umum: worker/agent sibuk, job lain berjalan, atau target belum merespons. Buka Monitor Center > Jobs, cek status dan Run Log; jangan submit job duplikat berkali-kali.

Apakah perlu mematikan backup job saat restore?

Tidak selalu. Yang lebih penting: pastikan restore tidak menulis ke prefix yang sedang dipakai produksi dan tidak berebut bandwidth kritis. Untuk perubahan besar, jadwalkan di change window dan koordinasikan dengan job backup lain.

Bagaimana cara memverifikasi hasil restore dengan benar?

Jangan berhenti di status Completed. Bandingkan daftar objek dan total ukuran, unduh beberapa sample, buka filenya, dan bandingkan checksum bila tersedia. Untuk audit, simpan manifest aws s3 ls --recursive sebagai lampiran tiket.

Apakah “Encrypted Transfer” harus selalu aktif?

Rekaman mematikan opsi ini karena berada di lab. Di produksi, aktifkan bila trafik melewati jaringan yang tidak sepenuhnya tepercaya. Enkripsi menambah overhead, jadi ukur dampaknya terhadap durasi job.
