Buka Object Storage dari menu Resources

Sebelum membuat job, pastikan Vinchin melihat object storage sebagai inventaris yang bisa dipakai. Di rekaman, daftarnya masih kosong dan pintu masuknya adalah Resources → Object Storage.

Apa yang kamu lakukan

  1. Login ke web console Vinchin sebagai admin.
  2. Di sidebar, buka Resources, lalu pilih Object Storage.
  3. Perhatikan toolbar: Add, Edit, License, dan Auto Refresh.
  4. Jika daftar kosong seperti di rekaman, lanjut ke tombol Add pada langkah berikutnya.
Hasil yang diharapkan: halaman Object Storage List terbuka dan tombol Add bisa diklik.

Kenapa ini penting

Object storage bukan sumber backup bawaan seperti VMware atau NAS. Tanpa entri di daftar ini, modul S3 Backup tidak punya kandidat sumber—wizard bisa terbuka, tetapi tidak ada storage yang bisa dipilih.

Menu ini juga tempat memantau Status dan Licensing Status, dua sinyal yang menentukan job boleh dibuat atau tidak.

Analogi praktis

Ini seperti mendaftarkan rak arsip ke katalog perpustakaan. Raknya sudah ada di gedung lain, tetapi selama belum masuk katalog, petugas tidak tahu di mana harus mencari.

Jebakan umum

Mencari menu yang salah. Object storage tidak ditambahkan dari dalam wizard backup job. Jika memulai dari S3 Backup → Backup saat daftar kosong, kamu akan berputar di wizard tanpa sumber.

Menganggap menu sama di semua peran. Akun non-admin bisa saja tidak melihat Resources. Pastikan memakai akun yang punya hak mengelola object storage, bukan hanya melihat job.

Pro-tip

Catat dulu tiga hal di samping layar: endpoint, nama storage yang akan dipakai, dan backup node tujuan. Tiga informasi ini akan diminta lagi di langkah 3 dan 6, dan mencarinya di tengah wizard hanya menambah risiko salah isi.

Tambah storage dan pilih vendor Ceph S3

Vendor menentukan dialek API dan field yang muncul. Di rekaman, pilihan jatuh ke Ceph S3—bukan Amazon S3 yang tampil sebagai default.

Apa yang kamu lakukan

  1. Klik Add untuk membuka dialog Add Object Storage.
  2. Buka dropdown Vendor. Perhatikan pilihan yang tersedia, jangan langsung menerima default.
  3. Pilih Ceph S3 sesuai storage yang dipakai di rekaman.
  4. Perhatikan field berubah: Server Endpoint, SSL Certificate, Username, Password, dan Object Storage Name.
Hasil yang diharapkan: form menampilkan field khas Ceph S3 dan siap diisi.

Kenapa ini penting

Vendor memengaruhi cara Vinchin menyusun request, menangani path bucket, dan membaca respons. Profil yang salah bisa lolos pengisian form, tetapi gagal saat sinkronisasi atau malah membaca objek dengan format yang keliru.

Analogi praktis

Seperti memilih bahasa saat menyambungkan printer jaringan. Alamat IP-nya sama, tetapi instruksi yang dikirim harus cocok dengan merek printer—kalau tidak, dokumen tidak pernah tercetak.

Jebakan umum

Menerima default Amazon S3. Itu pilihan pertama di dropdown, bukan pilihan yang benar untuk Ceph. Salah vendor adalah kesalahan paling mudah terjadi di layar ini.

Memilih “Other” tanpa alasan. Gunakan Other (S3 Compatible) hanya jika vendor tidak ada di daftar; untuk Ceph atau MinIO, pilih profil khususnya agar field dan perilakunya sesuai.

Pro-tip

Tanyakan satu kalimat ke pengelola storage: “Ini Ceph RGW, MinIO, atau S3-compatible generik?” Jawaban itu langsung menentukan vendor. Jangan menebak dari port atau nama bucket.

Isi endpoint, kredensial, dan nama storage

Semua field di layar ini saling terkait: alamat, protokol, dan kunci akses harus menggambarkan satu storage yang sama. Di rekaman, endpoint memakai HTTP sehingga SSL Certificate dibiarkan OFF.

Apa yang kamu lakukan

  1. Isi Server Endpoint dengan URL yang bisa dijangkau backup node—di rekaman 172.18.21.48:8080.
  2. Biarkan SSL Certificate OFF untuk endpoint HTTP ini. Jika storage memakai HTTPS, aktifkan dan pastikan sertifikatnya tepercaya.
  3. Isi Username dengan access key ID dan Password dengan secret access key.
  4. Beri Object Storage Name yang unik dan mudah dikenali—rekaman memakai ceph.
  5. Biarkan Backup Proxy OFF seperti di rekaman, lalu klik OK.
Hasil yang diharapkan: storage muncul di daftar dengan Status Normal, meski Licensing Status masih Unlicensed.

Kenapa ini penting

Endpoint adalah alamat yang dipakai backup node untuk membaca objek. Access key menentukan izin, sedangkan secret adalah bukti identitas. Kombinasi yang salah tidak akan terlihat sampai Vinchin mencoba sinkronisasi.

Nama storage menjadi label di seluruh UI—termasuk saat memilih sumber di langkah 5. Nama yang berantakan menyulitkan audit di kemudian hari.

Analogi praktis

Endpoint seperti alamat gedung, access key seperti nomor kartu akses, dan secret seperti PIN kartu. Gedungnya benar tetapi PIN salah tetap tidak membuka pintu—dan PIN tidak boleh ditempel di depan pintu.

Jebakan umum

SSL tidak cocok. Endpoint HTTP dengan SSL ON, atau HTTPS dengan SSL OFF, adalah sumber kegagalan koneksi yang sering terlewat. Samakan toggle dengan skema URL.

Port salah atau tidak terbuka. 8080 di rekaman belum tentu port di lingkunganmu. Uji keterjangkauan dari backup node, bukan dari laptop.

Secret key berisi spasi atau karakter terpotong. Tempel ulang dan periksa panjangnya; jangan mengetik manual dari foto.

Memakai kredensial admin storage. Buat kunci khusus backup dengan izin baca yang cukup, lalu simpan rahasianya di tempat aman.

Pro-tip

Sebelum mengisi form, jalankan uji port dari backup node—misalnya Test-NetConnection 172.18.21.48 -Port 8080 di PowerShell. Jika port tertutup, semua percobaan di UI akan berakhir sama.

Aktifkan lisensi sampai status Licensed

Storage yang sudah terdaftar belum tentu boleh dipakai. Di rekaman, status lisensi berubah dari Unlicensed menjadi Licensed setelah dialog lisensi dikonfirmasi.

Apa yang kamu lakukan

  1. Setelah storage ditambahkan, klik barisnya di Object Storage List.
  2. Klik License di toolbar.
  3. Di dialog Object storage authorization, pilih storage yang akan dilisensi.
  4. Konfirmasi lisensi. Di rekaman, dialog menampilkan Free/Used/Total: 9999/0/9999—angka demo, bukan patokan universal.
  5. Tunggu sampai Licensing Status berubah menjadi Licensed dan muncul notifikasi Authorization Added Successfully.
Hasil yang diharapkan: kolom Licensing Status berisi Licensed, bukan lagi Unlicensed.

Kenapa ini penting

Lisensi adalah gerbang komersial sekaligus teknis. Storage yang belum dilisensi bisa tampil di daftar, tetapi tidak boleh menjadi sumber job backup. Melewatkan langkah ini membuat wizard kehabisan sumber yang valid.

Analogi praktis

Mendaftarkan mobil ke katalog armada belum memberi izin jalan. Lisensi adalah stiker yang membuat mobil boleh dipakai mengangkut barang.

Jebakan umum

Mengira lisensi platform sudah mencakup semuanya. Object storage punya status lisensinya sendiri. Periksa kolom Licensing Status, bukan hanya status koneksi.

Melewati dialog karena notifikasi sudah hijau. Notifikasi “Object Storage added successfully” hanya berarti pendaftaran berhasil, bukan lisensi aktif.

Menganggap angka 9999 berlaku di semua instalasi. Itu nilai pada lingkungan demo. Cek kuota lisensi yang benar-benar tersedia.

Pro-tip

Setelah lisensi aktif, klik Auto Refresh sekali untuk memastikan status koneksi tetap Normal. Status lisensi yang benar tetapi koneksi putus tetap akan menggagalkan backup.

Buat job dan pilih objek sumber

Sekarang masuk ke modul S3 Backup. Di rekaman, sumbernya adalah storage ceph dan folder mail_backup; pilihan objek di dalamnya menentukan apa yang benar-benar disalin.

Apa yang kamu lakukan

  1. Di sidebar, buka S3 Backup, lalu klik Backup.
  2. Pada langkah Backup Source, centang storage ceph di panel kiri.
  3. Di panel kanan, perluas folder mail_backup.
  4. Centang objek yang ingin dilindungi—rekaman memilih 1.11.tar, db, fs, dan fs_parallel.
  5. Biarkan tab Wildcard Filter pada None karena tidak dipakai di rekaman, lalu klik Next.
Hasil yang diharapkan: daftar objek terpilih tercatat di ringkasan job, dan tombol Next aktif.

Kenapa ini penting

Job hanya melindungi apa yang dipilih. Memilih seluruh bucket memang terdengar aman, tetapi memperbesar waktu, ruang, dan biaya operasional. Sebaliknya, memilih terlalu sempit membuat objek penting tidak punya restore point.

Pilihan di sini juga memengaruhi retensi: semakin banyak objek, semakin cepat kuota restore point terpakai.

Analogi praktis

Seperti memilih barang yang masuk kotak pindahan. Kamu tidak memasukkan seluruh isi rumah hanya karena kotaknya besar; kamu memilih barang yang benar-benar perlu dibawa.

Jebakan umum

Mengira mencentang folder otomatis mencentang semua isinya. Periksa objek anaknya; di rekaman beberapa file dicentang terpisah.

Salah memahami wildcard. Exclusion membuang pola tertentu, Inclusion membatasi ke pola tertentu. Jangan mengisi filter hanya karena kolomnya tersedia.

Tidak ada objek terpilih. Tombol Next bisa tetap terlihat, tetapi job tanpa sumber tidak berguna. Pastikan setidaknya satu objek masuk daftar.

Pro-tip

Mulai dari satu folder pilot seperti mail_backup. Setelah restore point pertama terbukti bisa direstore, baru perluas cakupan. Ini jauh lebih aman daripada memilih seluruh bucket pada percobaan pertama.

Tentukan backup node dan storage tujuan

Inilah titik yang sering disalahpahami: tujuan backup bukan bucket S3, melainkan Local Disk1 pada backup node. S3 hanya sumber baca.

Apa yang kamu lakukan

  1. Pada langkah Backup Destination, pilih Target Node yang akan menjalankan penulisan—rekaman memakai vinchin811 (172.18.14.12).
  2. Pilih Target Storage—rekaman memakai Local Disk1 dengan kapasitas 99.95 GB dan free space 79.34 GB.
  3. Baca notice yang muncul: node dan storage harus dipilih sebelum job bisa berjalan.
  4. Klik Next menuju strategi backup.
Hasil yang diharapkan: node dan storage tujuan tampil di review, dengan sisa ruang yang cukup.

Kenapa ini penting

Backup node adalah mesin yang membaca sumber dan menulis data. Storage tujuan menentukan di mana restore point disimpan. Jika ruang habis, job berikutnya gagal meskipun sumber S3 sehat.

Memilih node yang salah juga memengaruhi throughput dan lokasi data saat restore—terutama jika kamu punya lebih dari satu node.

Analogi praktis

S3 adalah gudang asal. Backup node adalah truk yang memuat barang, dan Local Disk1 adalah gudang tujuan. Barang tidak kembali ke gudang asal hanya karena sudah dimuat.

Jebakan umum

Mengira backup ditulis ke S3. Di rekaman, tujuan fisiknya Local Disk1. Jangan merencanakan kapasitas bucket untuk data backup ini.

Memilih disk yang hampir penuh. Free space 79.34 GB terlihat besar, tetapi harus dibagi dengan retensi dan job lain. Hitung kebutuhan sebelum produksi.

Tidak memeriksa node aktif. Node yang sedang sibuk atau offline akan membuat job tertunda atau gagal.

Pro-tip

Sebelum memilih storage, bandingkan free space dengan ukuran sumber dan retensi. Di demo, satu restore point berukuran 1.42 GB dari sumber yang dipilih—angka ini bisa jauh berbeda di lingkunganmu.

Susun full + incremental, retensi, dan advanced strategy

Rekaman memakai Backup as scheduled: full backup setiap Jumat pukul 23:03 dan incremental harian pada jam yang sama. Retensi diset 30 restore point, dengan kompresi aktif.

Apa yang kamu lakukan

  1. Di General Strategy, pilih mode Backup as scheduled.
  2. Centang Full Backup, pilih Weekly, hari Friday, Start Time 23:03:00, Repeat OFF.
  3. Centang Incremental Backup, pilih Daily, Start Time 23:03:00, Repeat OFF.
  4. Periksa Data Storage Policy: compression ON, level Quick Compression, encryption OFF pada rekaman.
  5. Atur Retention Policy ke 30 restore point.
  6. Di Transmission Strategy, biarkan retry attempts 60 dan interval 30 detik; proxy dan encryption OFF.
  7. Di Advanced Strategy, aktifkan Skip Objects Alert dengan 10 objek dan 20%, lalu klik Next.
Hasil yang diharapkan: ringkasan strategi menampilkan full mingguan, incremental harian, retensi 30, dan alert aktif.

Kenapa ini penting

Full membuat baseline lengkap; incremental hanya mencatat perubahan. Kombinasi ini menghemat ruang dan waktu, tetapi tetap membutuhkan full yang sehat sebagai fondasi.

Retensi menentukan berapa lama kamu bisa kembali ke masa lalu. Kompresi menghemat kapasitas, sedangkan Skip Objects Alert memberi sinyal bila ada objek yang tidak terproses.

Analogi praktis

Full backup seperti album foto lengkap setiap minggu. Incremental seperti catatan harian tentang apa yang berubah. Retensi adalah berapa banyak album dan catatan yang kamu simpan di rak.

Jebakan umum

Full dan incremental di jam yang sama. Rekaman memakai 23:03 untuk keduanya. Di produksi, geser salah satu agar tidak berebut resource dan jangan sampai incremental berjalan sebelum full selesai.

Retensi terlalu kecil. 30 restore point bukan berarti 30 hari kalau full dan incremental sama-sama memakai slot. Hitung ulang dengan pola jadwalmu.

Menganggap alert sama dengan kegagalan. Skip Objects Alert memberi peringatan ketika ambang terlampaui; tetap periksa log untuk tahu objek mana yang terlewat.

Lupa zona waktu. Jam 23:03 mengikuti waktu server. Pastikan cocok dengan jendela operasional dan zona waktu tim.

Pro-tip

Jadwalkan full pada akhir pekan dan incremental di luar jam sibuk, misalnya full Jumat 23:03 dan incremental 01:10. Beri jeda agar full selesai sebelum delta pertama. Uji skenario ini di lab jadwal di bawah.

Review, submit, lalu start job

Submit hanya membuat job. Di rekaman, job muncul dengan status Pending dan baru berjalan setelah tombol Start ditekan.

Apa yang kamu lakukan

  1. Di langkah Review & Confirm, baca ulang nama job—rekaman memakai Object Storage Backup Job1.
  2. Verifikasi objek sumber, target node, storage, jadwal, dan retensi.
  3. Klik Submit. Tunggu notifikasi Backup job created successfully.
  4. Buka Monitor Center → Jobs. Job baru tampil dengan status Pending.
  5. Klik Start pada baris job, lalu konfirmasi.
Hasil yang diharapkan: status berubah dari Pending menjadi Running, dan halaman detail job bisa dibuka.

Kenapa ini penting

Review adalah kesempatan terakhir menangkap scope atau jadwal yang salah sebelum job menjadi bagian dari operasi. Setelah dibuat, perubahan tetap bisa dilakukan, tetapi lebih berisiko dan bisa mengacaukan jadwal.

Memahami beda submit dan start mencegah kebingungan “job sudah dibuat tetapi tidak ada data” yang sering muncul di tiket dukungan.

Analogi praktis

Submit seperti mencetak tiket antrean; Start seperti memanggil nomor tiket. Tiket yang sudah dicetak belum berarti pekerjaan dimulai.

Jebakan umum

Menganggap submit = jalan. Job akan tetap Pending sampai dijalankan manual atau menunggu jadwal berikutnya.

Nama job tidak informatif. Object Storage Backup Job1 cukup untuk demo, tetapi di produksi gunakan nama yang memuat sumber, tujuan, dan tujuan bisnis.

Tidak memeriksa ulang objek. Setelah submit, memperbaiki sumber berarti mengedit job; lebih murah menangkapnya di review.

Pro-tip

Jalankan full pertama secara manual setelah submit. Dengan begitu kamu punya baseline dan bukti restore point lebih cepat, tanpa menunggu Jumat 23:03.

Pantau job dan buktikan restore point

Job yang selesai bukan hanya soal progress bar. Bukti akhirnya ada di Backup Data: satu restore point full dengan ukuran yang masuk akal.

Apa yang kamu lakukan

  1. Buka Monitor Center → Jobs, lalu klik nama job untuk melihat detail.
  2. Pantau progress, speed, total size, processed, dan run log sampai status berubah menjadi Completed.
  3. Buka S3 Backup → Backup Data.
  4. Pilih job dan storage, lalu periksa Restore Point List.
  5. Pastikan ada restore point Full Backup dengan ukuran dan waktu yang sesuai.
  6. Lakukan uji restore satu file kecil untuk membuktikan data bisa dibaca kembali.
Hasil yang diharapkan: status Completed dan restore point Full Backup terlihat di Backup Data.

Kenapa ini penting

Backup yang tidak pernah diuji restore hanyalah asumsi. Restore point adalah bukti bahwa data benar-benar tersimpan dan bisa dipakai saat dibutuhkan.

Memantau run log juga membantu membedakan masalah sumber, jaringan, dan storage tujuan sebelum menjadi insiden.

Analogi praktis

Progress bar adalah resi pengiriman; restore point adalah barang yang benar-benar tiba di gudang. Kamu belum selesai sampai barangnya bisa dibuka kembali.

Jebakan umum

Berhenti di 100%. Di rekaman, progress sempat 100% tetapi status masih Running sesaat. Tunggu Completed sebelum menutup halaman.

Hanya melihat kecepatan. Throughput tinggi tidak menjamin semua objek terbaca. Periksa log dan jumlah objek.

Tidak pernah uji restore. Job Completed tanpa uji restore tetap menyisakan ketidakpastian tentang isi dan izin file.

Lupa retensi. Restore point lama akan terhapus saat batas retensi tercapai; pastikan kebijakan itu sesuai kebutuhan.

Pro-tip

Catat tiga bukti saat uji: timestamp restore point, ukuran data, dan hasil restore satu file. Simpan sebagai lampiran tiket perubahan—jauh lebih kuat daripada screenshot progress bar.

FAQ

Pertanyaan yang sering muncul

Jawaban singkat untuk kebingungan yang paling mungkin terjadi setelah menonton rekaman.

01 Apakah data S3 disalin kembali ke bucket S3?

Tidak. Pada rekaman, job membaca objek dari Ceph S3 lalu menulis restore point ke Local Disk1 milik backup node. Bucket sumber tetap menjadi sumber, bukan tujuan backup.

02 Bisakah membuat job sebelum object storage dilisensi?

Storage bisa terdaftar dan berstatus Normal, tetapi Licensing Status tetap Unlicensed. Job backup membutuhkan storage yang sudah Licensed. Selesaikan dialog License lebih dulu, lalu buktikan statusnya berubah.

03 Kapan memilih Ceph S3 dan kapan memilih Other (S3 Compatible)?

Pilih Ceph S3 bila storage-nya Ceph RGW. Pilih MinIO untuk MinIO. Gunakan Other (S3 Compatible) hanya jika penyedia tidak ada di daftar vendor. Jangan memakai Amazon S3 hanya karena itu pilihan pertama.

04 Mengapa job baru berstatus Pending?

Submit hanya membuat definisi job. Job berjalan saat kamu menekan Start atau saat jadwal berikutnya tiba. Di rekaman, Start ditekan manual setelah job muncul di Current Jobs.

05 Apakah 30 restore point berarti 30 hari?

Belum tentu. Full dan incremental sama-sama menghasilkan restore point. Dengan full mingguan dan incremental harian, 30 slot tidak otomatis berarti 30 hari kalender. Hitung ulang berdasarkan pola jadwal dan kebutuhan RPO/RTO.

06 Apa yang terjadi jika full dan incremental dijadwalkan pada jam yang sama?

Keduanya bisa berebut resource dan membuat urutan run tidak ideal. Rekaman memakai 23:03 untuk keduanya karena bersifat demo. Di produksi, beri jeda—misalnya full 23:03 dan incremental 01:10—agar full selesai lebih dulu.

07 Di mana saya bisa memastikan backup benar-benar berhasil?

Buka S3 Backup → Backup Data, pilih job dan storage, lalu lihat Restore Point List. Bukti yang lebih kuat adalah melakukan uji restore satu file kecil dan mencatat waktu serta ukurannya.

08 Apakah modul ini menggantikan dokumentasi resmi?

Tidak. Modul ini adalah alat belajar berdasarkan rekaman demo. Nama menu, field, dan perilaku dapat berbeda antarversi atau antarinstalasi. Selalu verifikasi di lingkunganmu dan ikuti dokumentasi resmi Vinchin.
