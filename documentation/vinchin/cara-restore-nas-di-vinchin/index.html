Mental model

Yang terjadi di balik tombol Restore

Restore bukan sekadar menyalin folder. Vinchin membaca blok data dari rantai restore point, menyusunnya kembali menjadi file, menulis ke share tujuan, lalu mencatat setiap tahap di run log.

Empat komponen, satu alur

Klik node pada diagram untuk melihat perannya. Urutannya selalu sama, baik restore satu file maupun seluruh share.

  1. 1Titik waktu. Restore point menentukan versi data: full, incremental, atau differential.
  2. 2Rantai data. Differential butuh full induknya; incremental butuh seluruh rantai sebelumnya.
  3. 3Tujuan tulis. Share dan path menentukan apakah data ditimpa atau ditulis ke jalur uji.
  4. 4Verifikasi. Status Completed belum cukup—buka file dan bandingkan isinya.

Buka NAS Restore dan kenali empat tahap wizard

Restore adalah job baru, bukan tombol “undo” di halaman backup. Sebelum mengisi apa pun, pastikan kamu berada di modul NAS Backup dan memahami urutan layarnya.

Apa yang kamu lakukan

  1. Login ke konsol Vinchin memakai akun admin: https://<IP-Vinchin>. Di video: https://172.18.24.34.
  2. Periksa menu kiri. Pastikan kamu membuka NAS Backup, lalu pilih Restore—bukan VM Backup atau Physical Backup.
  3. Tunggu halaman New Job terbuka. Empat lingkaran tahap harus terlihat, dengan tahap 1 Restore Point aktif.
  4. Catat konteks awal: nama node, share sumber, dan daftar job yang muncul. Ini baseline sebelum kamu mengubah pilihan.
  5. Jangan langsung menekan Next. Pahami dulu bahwa setiap tahap mengunci keputusan yang memengaruhi luas dan tujuan penulisan data.

Mengapa ini penting

Wizard restore memisahkan sumber, tujuan, dan strategi. Memisahkan langkah ini membuat kamu bisa memeriksa ulang sebelum data ditulis.

Membuka modul yang salah adalah penyebab umum: daftar restore point kosong, lalu operator menyimpulkan “backup tidak ada” padahal yang dibuka adalah modul VM.

Analogi praktis

Anggap konsol Vinchin sebagai meja arsip. Kamu harus memilih lemari yang benar (NAS), memilih tanggal arsip (restore point), lalu menentukan meja tujuan penulisan (share dan path).

Wizard adalah petugas yang menanyakan satu hal pada satu waktu—bukan formulir panjang yang bisa diisi acak.

Jebakan umum

  • Salah modul. NAS Restore ada di NAS Backup → Restore. VM dan Physical Backup punya daftar restore point sendiri.
  • Menganggap peringatan sertifikat sebagai kegagalan. Konsol lab memakai HTTPS self-signed; verifikasi sidik jari sertifikat sebelum melanjutkan.
  • Mengira “Job has been deleted” berarti restore point hilang. Job bisa dihapus, tetapi restore point lama masih tersimpan.
  • Melanjutkan saat node sumber offline. Daftar bisa tampil dari cache, tetapi pembacaan data akan gagal saat job berjalan.

Pro-tip

  • Buka restore di tab terpisah dari halaman monitoring agar kamu bisa membandingkan status job lama dan baru.
  • Catat URL, nama node, dan waktu konsol di tiket. Jika timezone server berbeda dari laptop, timestamp restore point bisa terlihat “ bergeser”.
  • Untuk latihan, jangan pakai akun admin produksi. Buat akun operator dengan hak restore terbatas.

Pilih restore point: titik waktu yang ingin dipulihkan

Satu job bisa punya banyak restore point. Memilih yang terbaru belum tentu benar—terutama jika insiden baru terjadi setelah data rusak atau terenkripsi.

Apa yang kamu lakukan

  1. Biarkan Select restore point pada All nodes, atau pilih node sumber jika daftar terlalu panjang.
  2. Gunakan kotak Search by job name… untuk menyaring job, misalnya NAS Backup Job2.
  3. Klik ikon + di samping job, lalu perluas node sumber 172.18.1.100(/cifs).
  4. Pilih satu restore point. Di video dipilih 2023-02-17 16:27:44 (Differential Backup).
  5. Pastikan panel kanan NAS Restore Source berubah menampilkan isi titik waktu tersebut sebelum lanjut.

Mengapa ini penting

Restore point menentukan isi file pada detik tertentu. Memilih titik setelah kerusakan berarti memulihkan data yang sudah rusak.

Jenis backup juga menentukan ketergantungan. Differential membutuhkan full induknya; incremental membutuhkan seluruh rantai. Jika satu bagian rantai hilang, restore bisa gagal.

Full 16:25:44→Incremental 16:26:06→Full 16:27:03→Diff 16:27:44

Analogi praktis

Restore point seperti slot save game. Full adalah save lengkap; incremental adalah perubahan sejak save terakhir; differential adalah perubahan sejak save lengkap terakhir.

Memilih Differential 16:27:44 berarti kamu membutuhkan Full 16:27:03 sebagai fondasi—bukan Full paling awal.

Jebakan umum

  • Selalu memilih yang paling baru. Untuk ransomware atau salah hapus, pilih titik sebelum insiden terjadi.
  • Mengabaikan label “Job has been deleted”. Restore point tetap ada, tetapi kamu kehilangan jadwal backup baru dari job tersebut.
  • Memilih differential tanpa full induk. Rantai harus lengkap; cek riwayat dan status full terakhir.
  • Bingung timezone. Timestamp mengikuti waktu server; bandingkan dengan jam insiden di tiket.

Pro-tip

  • Untuk uji coba, pilih satu restore point yang sudah dikenal isinya, lalu restore satu folder kecil. Jangan mulai dari seluruh share produksi.
  • Catat timestamp, tipe backup, dan nama job di tiket. Ini memudahkan audit saat hasil restore dipertanyakan.
  • Jika restore point yang dibutuhkan tidak ada, jangan memaksa. Periksa retensi, job history, dan repository sebelum mencari alternatif.

Batasi cakupan: pilih /nas atau folder tertentu

Semakin luas cakupan, semakin lama restore dan semakin besar ruang yang dibutuhkan. Untuk pemulihan file tertentu, jangan langsung mencentang seluruh share.

Apa yang kamu lakukan

  1. Perluas node sumber 172.18.1.100(/cifs) hingga terlihat root /nas.
  2. Klik + pada /nas untuk melihat subfolder. Di video muncul dua folder dengan nama UUID panjang.
  3. Centang root /nas bila ingin memulihkan seluruh share, atau centang folder spesifik untuk restore granular.
  4. Perhatikan daftar di panel kanan bertambah sesuai pilihan. Item yang dicentang adalah yang akan ditulis ke tujuan.
  5. Klik Next hanya setelah cakupan sesuai tiket. Di video, root /nas dipilih.

Mengapa ini penting

Cakupan menentukan jumlah file yang ditulis, kebutuhan ruang, dan durasi. Restore seluruh share bisa menimpa banyak file yang sebenarnya masih baik.

Restore granular juga lebih mudah diverifikasi: kamu bisa membandingkan satu folder hasil restore dengan sumbernya tanpa mengganggu share produksi.

root = semua isi subfolder = selektif panel kanan = konfirmasi

Analogi praktis

Seperti memindahkan barang dari gudang: kamu bisa membawa satu kardus atau seluruh rak. Membawa seluruh rak memang lengkap, tetapi lebih lama dan lebih berisiko salah tempat.

Untuk uji, bawa satu kardus dulu—satu folder kecil—lalu periksa isinya.

Jebakan umum

  • Mencentang root karena “biar aman”. Justru sebaliknya: cakupan besar memperbesar risiko overwrite dan durasi.
  • Ikut memulihkan @Recycle atau @Recently-Snapshot. Folder sistem seperti ini biasanya tidak perlu untuk restore data.
  • Tertukar folder UUID. Nama teknis tidak selalu sama dengan nama tampilan; cocokkan dengan struktur asli.
  • Lupa memeriksa panel kanan. Centang di pohon belum tentu sama dengan daftar final; lihat konfirmasinya.

Pro-tip

  • Mulai dari satu folder kecil yang kamu kenal isinya. Setelah verifikasi berhasil, baru pertimbangkan cakupan lebih besar.
  • Catat daftar file yang dipilih. Jika perlu, screenshot panel kanan dan lampirkan ke tiket perubahan.
  • Jika folder tampak kosong, jangan langsung menyimpulkan backup gagal—periksa apakah restore point yang dipilih memang berisi data tersebut.

Pilih NAS Share tujuan, bukan sekadar “di mana saja”

Tujuan restore adalah share yang ditulis oleh Vinchin, bukan folder di laptop kamu. Share harus terdaftar, reachable, dan punya izin tulis.

Apa yang kamu lakukan

  1. Pada Restore to, pilih NAS Share. Ini menentukan bahwa tujuan adalah share yang dikelola Vinchin.
  2. Di Select NAS Share, perluas node 172.18.1.100 dan pilih share tujuan—di video: cifs.
  3. Perhatikan protokol di nama share: Judy_CIFS (SMB/CIFS) atau Judy_NFS (NFS). Jangan mencampur asumsi permission.
  4. Pastikan share tidak sedang offline. Jika daftar kosong atau abu-abu, periksa koneksi dan kredensial dari sisi Vinchin.
  5. Klik Next untuk masuk ke pemilihan path. Tujuan belum ditulis sampai job dijalankan.

Mengapa ini penting

Share tujuan menentukan di mana byte benar-benar ditulis. Salah share bisa berarti data masuk ke perangkat yang salah, atau gagal karena izin.

CIFS/SMB dan NFS punya model izin berbeda. Share yang bisa dibaca belum tentu bisa ditulis oleh akun yang dipakai Vinchin.

Analogi praktis

Ini seperti memilih alamat pengiriman. Barang bisa dikemas sempurna, tetapi jika alamatnya salah, paket tidak sampai—atau masuk ke rumah orang lain.

Protokol adalah jenis kurir: CIFS/SMB dan NFS punya aturan serah-terima yang berbeda.

Jebakan umum

  • Memilih share sumber sebagai tujuan. Restore langsung ke share produksi; untuk uji, gunakan share/path terpisah.
  • Menganggap CIFS dan NFS setara. Permission, UID/GID, dan dukungan ACL berbeda. Pilih sesuai platform tujuan.
  • Ruang tidak cukup. Restore bisa berhenti di tengah dan meninggalkan file parsial.
  • Share terdaftar tetapi tidak reachable. Daftar bisa muncul dari konfigurasi lama; uji koneksi sebelum Submit.

Pro-tip

  • Buat share khusus restore, misalnya restore-staging, dengan kuota dan izin terbatas. Ini memisahkan data uji dari produksi.
  • Uji tulis sederhana dari host lain ke share yang sama sebelum menjalankan job besar.
  • Catat protokol dan nama share persis seperti di konsol—bukan hanya “NAS kantor”.
Di video: ketiga share berasal dari node yang sama (172.18.1.100) dengan nama berbeda. Nama share adalah label yang dibuat saat pendaftaran, bukan nama volume fisik.

Tentukan restore path: timpa di tempat atau uji di jalur terpisah

Ini keputusan paling berisiko di seluruh wizard. Recover to the original path mengembalikan file ke lokasi asal; Manually select path memungkinkan kamu menulis ke folder uji.

Apa yang kamu lakukan

  1. Buka dropdown Restore Path. Pilih Recover to the original path untuk rollback ke lokasi asal.
  2. Atau pilih Manually select path lalu telusuri pohon folder tujuan dan tentukan folder baru, misalnya /restore-test/2026-10-27.
  3. Jika memilih manual, pastikan folder tujuan berada di share yang dipilih pada langkah 4—bukan share lain.
  4. Periksa kembali apakah path sudah ada. Folder yang sudah ada berpotensi ditimpa atau digabung.
  5. Lanjutkan ke Restore Strategy. Path final masih akan terlihat di Review & Confirm.

Original path

Kembalikan file ke lokasi asal di share sumber. Cocok untuk rollback penuh setelah insiden.

  • File lama bisa tertimpa
  • Tidak ada ruang tambahan untuk salinan uji
  • Perlu jendela maintenance
  • Perlu izin pemilik data

Alternate path

Tulis ke folder baru, misalnya /restore-test/2026-10-27. Cocok untuk validasi dan latihan.

  • Produksi tetap utuh
  • Bisa dibandingkan berdampingan
  • Butuh ruang tambahan
  • Perlu pembersihan setelah uji

Mengapa ini penting

Path menentukan apakah restore bersifat destruktif. Original path menulis ke lokasi yang mungkin masih dipakai pengguna; manual path membuat salinan terpisah yang bisa diuji tanpa mengubah produksi.

Di video, pilihan original path konsisten dengan tujuan demo: mengembalikan /nas ke lokasi backup aslinya. Untuk latihan mandiri, pilihan itu belum tentu tepat.

Analogi praktis

Original path seperti mengembalikan furnitur ke kamar asalnya—cepat, tetapi jika kamar masih dipakai, barang lama bisa tertimpa. Alternate path seperti menaruhnya di gudang uji terlebih dahulu.

Jebakan umum

  • Memilih original path saat latihan. Kamu bisa menimpa data produksi dengan versi lama tanpa sengaja.
  • Mengira “manual” otomatis membuat folder baru. Pastikan folder tujuan ada dan bisa ditulis, atau buat sesuai panduan.
  • Menulis ke root share. Path seperti / atau /nas dapat bercampur dengan data lain.
  • Lupa permission. Folder baru mungkin mewarisi ACL yang salah; file bisa tidak terbaca pengguna akhir.

Pro-tip

  • Untuk restore drill, selalu gunakan alternate path dengan tanggal di nama folder. Setelah verifikasi, hapus atau arsipkan.
  • Simpan path tujuan di tiket dan di nama job. Contoh: NAS-RESTORE-INC1234-20261027.
  • Jika harus original path, lakukan di jendela maintenance dan pastikan snapshot atau backup baru sudah ada.
Perhatian: original path dapat menimpa file yang lebih baru. Jangan memilihnya hanya karena lebih cepat—pastikan kamu memang ingin mengganti isi lokasi asal.

Atur Restore Strategy dan Speed Controller

Restore bisa memakan bandwidth dan I/O besar. Strategi yang tepat menjaga agar proses pemulihan tidak justru mengganggu layanan yang masih berjalan.

Apa yang kamu lakukan

  1. Periksa tab General Strategy. Di sinilah pengaturan dasar restore berada.
  2. Buka Speed Controller bila perlu membatasi bandwidth. Di video, panel dibuka lalu ditutup; hasil akhirnya N/A.
  3. Jika menambahkan policy, tentukan jadwal dan batas kecepatan yang tidak bentrok dengan backup atau jam sibuk.
  4. Buka Advanced Strategy untuk melihat Transfer Threads. Nilai awal di video adalah 3.
  5. Jangan langsung Next. Nilai speed dan thread akan muncul di Review; pastikan kamu tahu angka akhirnya.

Mengapa ini penting

Restore membaca dari repository dan menulis ke NAS tujuan. Keduanya berbagi jaringan dan disk dengan produksi. Tanpa batas, job bisa menghabiskan bandwidth yang dibutuhkan aplikasi.

Speed Controller bukan mempercepat, melainkan membatasi agar dampak ke layanan lain terkendali. Thread mengatur seberapa banyak pekerjaan paralel yang diizinkan.

Analogi praktis

Speed Controller seperti batas kecepatan di jalan tol: kamu bisa menahan laju agar tidak membahayakan kendaraan lain. Transfer Threads seperti jumlah lajur—lebih banyak lajur bisa melancarkan, tetapi tetap dibatasi lebar jalan.

Jebakan umum

  • Menganggap Speed Controller wajib. Tanpa policy, restore memakai bandwidth yang tersedia—bisa membanjiri link produksi.
  • Membatasi terlalu rendah. Job melewati jendela maintenance dan berjalan saat jam kerja.
  • Policy bentrok dengan backup. Dua job besar bersamaan memperebutkan storage dan jaringan.
  • Mengira speed hanya memengaruhi restore. Policy bisa berlaku pada job lain; baca cakupannya.

Pro-tip

  • Mulai tanpa speed limit untuk lingkungan lab, lalu ukur dampaknya. Di produksi, batasi sekitar 60–70% kapasitas link sebagai titik awal.
  • Jadwalkan restore di luar jendela backup. Jika harus bersamaan, prioritaskan restore dan tunda backup non-kritis.
  • Dokumentasikan policy: nama, jam berlaku, batas, dan siapa yang menyetujui.

Sesuaikan Transfer Threads, lalu baca ulang angkanya

Menambah thread bisa mempercepat, tetapi hanya sampai bottleneck berikutnya—jaringan, CPU NAS, atau disk. Angka yang diketik harus benar-benar muncul di Review.

Apa yang kamu lakukan

  1. Buka Advanced Strategy dan temukan field Transfer Threads. Nilai awal di video: 3.
  2. Ubah ke angka yang sesuai kapasitas. Video mengetik 32; jangan jadikan angka ini default tanpa pengukuran.
  3. Klik di luar field atau tekan Tab agar nilai tersimpan, lalu buka kembali panel untuk memastikan angkanya bertahan.
  4. Lanjut ke Review. Di video, bagian Advanced Strategy masih menampilkan Transfer Threads: 3—bukan 32.
  5. Jika Review tidak sama dengan yang kamu ketik, kembali ke langkah ini dan perbaiki sebelum Submit.

Mengapa ini penting

Transfer Threads menentukan jumlah aliran data paralel. Pada link gemuk dan storage cepat, menambah thread bisa meningkatkan throughput. Pada link 1 GbE atau NAS dengan CPU lemah, thread berlebih justru menambah overhead.

Nilai yang tidak konsisten antara form dan Review adalah tanda bahwa perubahan belum tersimpan—atau field kembali ke default.

Analogi praktis

Bayangkan kasir supermarket. Menambah kasir mengurangi antrean sampai jumlah pelanggan yang bisa masuk toko menjadi batas. Setelah itu, menambah kasir tidak membantu—hanya menambah biaya.

Jaringan dan storage adalah pintu masuk toko; thread adalah jumlah kasir.

Jebakan umum

  • Menganggap 32 selalu lebih cepat. Bottleneck bisa berpindah ke CPU NAS, disk latency, atau session limit SMB.
  • Tidak memeriksa Review. Di video, angka 32 yang diketik tidak terlihat di Review—Review tetap 3.
  • Mengubah saat job lain berjalan. Throughput total bisa turun karena dua job bersaing.
  • Mengabaikan stabilitas. Terlalu banyak koneksi bisa memicu timeout atau error pada share tertentu.

Pro-tip

  • Titik awal praktis: 4–8 thread untuk 1 GbE, 8–16 untuk 10 GbE. Ukur durasi dan error sebelum menaikkan.
  • Uji dengan satu folder kecil. Jika waktu tidak membaik setelah menambah thread, bottleneck ada di tempat lain.
  • Catat nilai final dari Review, bukan dari form. Itulah yang benar-benar dikirim ke job.

Halaman Review merangkum seluruh keputusan. Ini kesempatan terakhir untuk menangkap sumber, titik waktu, tujuan, atau path yang salah sebelum job dibuat.

Apa yang kamu lakukan

  1. Isi Job Name. Di video: NAS Restore Job1. Gunakan nama unik yang memuat tiket dan tanggal.
  2. Periksa Data source dan The data source job: harus menunjuk share dan job backup yang benar.
  3. Periksa Restore Point dan Restore the file list. Pastikan titik waktu dan cakupan sesuai tiket.
  4. Periksa Restore Path, Mode, Advanced Strategy, dan Speed Controller. Di video: original path, once-off, 3 threads, speed N/A.
  5. Jika semuanya cocok, klik Submit. Setelah itu muncul toast “Create Restore Job success” dan job masuk ke daftar.

Mengapa ini penting

Job restore tidak memiliki tombol undo. Setelah Submit, Vinchin akan membaca dan menulis sesuai konfigurasi. Review adalah satu-satunya tempat untuk melihat semua keputusan secara bersamaan.

Perhatikan juga inkonsistensi: nilai thread di form bisa berbeda dari Review. Yang tampil di Review-lah yang akan dijalankan.

Analogi praktis

Seperti checklist sebelum pesawat lepas landas: semua item sudah diisi, tetapi pilot tetap membaca ulang bahan bakar, tujuan, dan jalur. Review bukan formalitas—ia mencegah kesalahan yang mahal.

Jebakan umum

  • Langsung Submit tanpa membaca. Path “original” yang tidak disengaja bisa menimpa produksi.
  • Nama job generik. NAS Restore Job1 sulit dibedakan saat ada beberapa percobaan.
  • Mengabaikan perbedaan nilai. Thread 32 di form tetapi 3 di Review adalah sinyal untuk kembali.
  • Menekan Submit dua kali. Tunggu respons; job bisa terbuat ganda jika terburu-buru.

Pantau job sampai Completed, lalu verifikasi isi file

“Create Restore Job success” hanya berarti job berhasil dibuat—bukan data sudah kembali. Pantau status, baca run log, lalu buktikan file bisa dibuka di tujuan.

Apa yang kamu lakukan

  1. Buka Monitor Center → Jobs. Cari job di Current Jobs; status awal di video adalah Pending.
  2. Klik nama job NAS Restore Job1 untuk membuka Job Details.
  3. Periksa Job Flow dan Summary: nama, tipe Restore, status Running, start time, dan durasi.
  4. Baca Run Log. Di video muncul tiga baris sukses, diakhiri “Obtain total restore data size completed”.
  5. Tunggu toast Job Completed. Job akan pindah ke History Jobs; buka kembali untuk konfirmasi akhir.
  6. Verifikasi di NAS tujuan: jumlah file, ukuran, buka sampel file, dan bandingkan checksum bila memungkinkan.

Mengapa ini penting

Submitted ≠ restored. Job bisa Pending karena antrean, atau Running lalu gagal di tengah. Run log menunjukkan tahap mana yang sudah dan belum selesai.

Verifikasi file adalah bukti sebenarnya: file ada, ukurannya wajar, dan bisa dibuka. Tanpa itu, kamu hanya percaya pada status UI.

Analogi praktis

Seperti melacak paket: “resi dibuat” bukan berarti paket sampai. Kamu menunggu status delivered, lalu membuka paket untuk memastikan isinya tidak rusak.

Jebakan umum

  • Menganggap toast “success” sebagai akhir. Itu hanya konfirmasi pembuatan job; statusnya masih Pending.
  • Tidak membaca run log. Kegagalan di tengah bisa tersamarkan oleh status yang tampak berjalan.
  • Memeriksa path yang salah. Original path dan manual path menghasilkan lokasi berbeda.
  • Lupa permission/ACL. File ada tetapi tidak bisa dibaca pengguna akhir—restore belum benar-benar selesai.

Pro-tip

  • Uji satu file kecil lebih dulu: buka, cek isi, lalu bandingkan hash dengan sumber jika tersedia.
  • Catat durasi, throughput, dan jumlah file di tiket. Data ini membantu menyetel thread pada restore berikutnya.
  • Jadikan restore drill rutin. Backup yang belum pernah direstore belum terbukti bisa dipulihkan.

FAQ

Pertanyaan yang sering muncul

Jawaban teknis singkat untuk situasi di luar demo video.

Apakah restore bisa berjalan saat backup sedang berjalan?
Bisa, tetapi keduanya bersaing untuk bandwidth, CPU, dan I/O storage. Hindari menjalankan bersamaan di produksi. Jika terpaksa, gunakan Speed Controller, tunda backup non-kritis, dan pantau latency NAS. Restore biasanya lebih diprioritaskan karena menyangkut pemulihan layanan.
Apakah differential backup butuh full backup induknya?
Ya. Differential menyimpan perubahan sejak full terakhir, jadi restore membutuhkan full induk yang tepat. Di video, Differential 16:27:44 membutuhkan Full 16:27:03. Incremental lebih ketat lagi: butuh seluruh rantai sampai full pertama. Jika satu bagian hilang, restore bisa gagal.
Mengapa restore point muncul padahal job-nya “has been deleted”?
Menghapus job backup menghapus jadwal dan konfigurasi job, bukan otomatis seluruh data restore point. Selama retensi dan repository masih menyimpan titik tersebut, restore tetap bisa dilakukan. Namun tidak ada backup baru dari job itu—periksa apakah kamu perlu membuat job pengganti.
Bisakah hanya satu file atau satu folder yang direstore?
Bisa. Pada tahap NAS Restore Source, perluas root share dan centang folder/file tertentu. Ini disebut restore granular. Manfaatnya: lebih cepat, kebutuhan ruang lebih kecil, dan risiko menimpa data lain menurun. Verifikasi tetap wajib.
Apakah restore selalu menimpa data yang ada?
Tidak selalu. Original path menulis ke lokasi asal sehingga berpotensi menimpa; manual/alternate path menulis ke folder lain. Di video dipilih original path karena tujuannya mengembalikan /nas ke lokasi backup. Untuk latihan atau audit, gunakan alternate path lebih dulu.
Berapa lama restore selesai?
Tergantung ukuran data, throughput, jumlah file kecil, latency, dan thread. Hitung kasar: ukuran ÷ throughput efektif. Di lab, 1.8 TB pada 480 MB/s ≈ 1 jam 4 menit. File kecil dalam jumlah besar bisa jauh lebih lambat daripada satu file besar berukuran sama.
Job berstatus Pending terus—apa yang harus dilakukan?
Periksa antrean job, koneksi ke node sumber/tujuan, kredensial share, dan apakah ada job lain yang berjalan. Buka Job Details dan lihat run log. Jika tidak ada progres, hentikan dengan hati-hati, perbaiki penyebab, lalu buat job baru. Jangan menghapus restore point untuk “membersihkan” antrean.
Apakah NAS perlu di-reboot setelah restore?
Biasanya tidak. Restore menulis file ke share; layanan NAS tidak perlu reboot hanya karena itu. Namun aplikasi yang memakai file mungkin perlu di-reload atau di-restart agar membaca versi baru. Ikuti prosedur aplikasi dan koordinasikan dengan pemilik layanan.
Langkah berikutnya

Ulangi alur ini di lab—bukan di produksi.

Pilih satu folder kecil, restore ke alternate path, lalu bandingkan hasilnya. Setelah yakin, baru susun runbook untuk restore produksi.
